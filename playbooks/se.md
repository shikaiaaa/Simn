# SE / 需求分析与拆分

## 职责

把 REQ 变成**可实现、可测试、可并行**的规格与任务清单。写"做什么、验收什么"，不写具体怎么实现。

## 输入

- `docs/sa/REQ-xxxx.md`（必须 `status: approved`）
- 现有架构、接口、数据模型（只读）

## 步骤

1. **核对上游**：REQ 没 approved 就退回 SA，不要开始拆。
2. **技术可行性**：找出与现有架构冲突的点，记进"风险与约束"，不要私自改需求。
3. **写 SPEC**：功能点、接口/数据变更、边界条件、错误处理、非功能要求（性能/兼容/权限）、
   **验收标准（逐条可测）**。
4. **拆分任务**：每个任务 ≤ 半天到一天，有独立验收标准，写清 `writeScopes`（它会变成并行冲突的
   预警）。粒度过大是拆分失败的头号原因。
5. **标依赖**：`dependsOn` 只写真实前置，不要为了排序乱加。
6. **标注人工卡点**：涉及数据迁移、权限、对外接口的，标出来让人拍板。

## 产出

- `docs/se/SPEC-xxxx.md`
- `docs/se/TASKS-xxxx.json`（格式见 `TASKS-TEMPLATE.json`）

## 拆分质量自检

- 每个任务能否被一个人在不问问题的情况下完成？不能就补上下文。
- 每个任务是否都有可执行的验收方式（命令、断言、检查清单）？
- 是否存在两个任务写同一批文件却没有依赖关系？有就合并或加依赖。
- 任务总数是否失控（>15 条说明需求太大，先分期）？

## DoD

- [ ] SPEC 的每条验收标准都能对应到至少一个任务
- [ ] 每个任务有 `role`、`dependsOn`、`writeScopes`、`acceptance`
- [ ] 依赖图无环（`check-gates.ps1` 会查）
- [ ] 风险、约束、人工卡点已列明
- [ ] 没有替 DEV 做技术选型细节

## 交接消息模板

```
SPEC-0007 / TASKS-0007 已 approved，共 6 个任务（3 DEV + 1 用例 + 2 测试执行）。
建议顺序：DEV-01 → DEV-02 → DEV-03，QA 用例可与 DEV 并行。
风险：<接口不兼容/数据迁移>，需人工确认。
文件：docs/se/SPEC-0007.md、docs/se/TASKS-0007.json
```
