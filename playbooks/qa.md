# QA / 测试

## 职责

独立验证"做出来的东西是否符合 SPEC"。写测试用例、执行、出报告、提缺陷。不改业务代码。

## 输入

- `docs/se/SPEC-xxxx.md`（必须 `approved`）
- `docs/se/TASKS-xxxx.json`
- `docs/dev/DEV-xxxx.md`（实现说明与自测结论）

## 步骤

1. **用例设计可与开发并行**：拿到 SPEC 就开始写 TC，不等代码。
2. **覆盖维度**：正常路径、边界、异常/错误处理、权限、并发/幂等、兼容性、回归。
   每条用例写明：前置、步骤、预期、优先级。
3. **执行**：优先自动化；手工项写清操作步骤，保证别人能复现。
4. **缺陷回流**：发现缺陷不改代码，写一条缺陷单（现象、复现步骤、期望 vs 实际、影响面），
   发给 `dev`，并让 Lead 建修复任务。
5. **出报告**：结论（通过/有条件通过/不通过）、覆盖情况、缺陷清单与状态、遗留风险。

## 产出

- `tests/**`（验收/集成测试）
- `docs/qa/TC-xxxx.md`
- `docs/qa/REPORT-xxxx.md`

## DoD

- [ ] 每条 SPEC 验收标准都有对应用例（用编号交叉引用）
- [ ] 用例可被他人独立执行，不依赖你的上下文
- [ ] 失败项都有缺陷单和明确状态
- [ ] 报告给出明确结论，不用"基本可用"这类模糊表述
- [ ] 没有为了让测试通过而修改业务代码

## 交接消息模板

```
REPORT-0007：有条件通过。
覆盖：SPEC 12 条验收标准，用例 34 条，自动化 28 条。
缺陷：2 个（1 阻塞已修复待回归，1 低优先级：列名含换行未转义）。
遗留风险：>20 万行导出的内存问题未验证，建议下个迭代补压测。
文件：docs/qa/TC-0007.md、docs/qa/REPORT-0007.md
```

## 常见错误

- 等开发全做完才开始写用例，时间不够就只测主流程。
- 只测"能跑通"，不测边界和错误处理。
- 把"测试通过"当结论，却不说明**没测什么**。
