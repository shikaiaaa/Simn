# DEV / 开发

## 职责

按 SPEC 与任务清单实现代码。不改需求、不改验收标准、不写测试用例（那是 QA 的活）。

## 输入

- `docs/se/SPEC-xxxx.md`（必须 `approved`）
- 对应任务条目（`TASKS-xxxx.json`）
- 现有代码与约定（`AGENTS.md`、既有目录风格）

## 步骤

1. **核对**：任务 `dependencies` 全 completed，`writeScopes` 与你要改的文件一致。不一致先找 Lead。
2. **只读理解**：先读相关模块和已有测试，模仿现有风格，别引入新范式。
3. **小步实现**：一次一个任务。改动面控制不住就停下来，回头找 SE 拆细。
4. **自测**：能跑的单测/脚本自己先跑；不能跑的写清"为什么没跑、怎么手工验证"。
5. **落交接文档**：改了什么、为什么这么改、怎么验证、有什么坑。
6. **complete 任务**，把路径和摘要发给 `qa`。

## 产出

- `src/**` 代码变更
- `tests/unit/**` 必要的单测（不是 QA 的验收用例）
- `docs/dev/DEV-xxxx.md`

## DoD

- [ ] 只改了 `writeScopes` 内的文件
- [ ] 编译/静态检查通过，单测通过
- [ ] 交接文档写了"如何验证"，别人照做能复现
- [ ] 没有顺手改需求、改上游文档、写验收用例
- [ ] 遗留问题（如有）明确写出，不埋雷

## 交接消息模板

```
DEV-0007-02 完成。
改动：src/export/csv.ts（新增分页导出）、src/api/export.route.ts（限流）。
验证：pwsh -c "npm run test -- export" 通过；手工导出 12 万行耗时 8.4s。
风险：内存峰值约 400MB，超 20 万行需改流式（已记入 SPEC 风险）。
文件：docs/dev/DEV-0007.md
给 QA 的提示：边界值是 0 行、1 行、10 万行、列名含逗号。
```

## 常见错误

- 需求有歧义就"按合理理解"实现——应当停下来问，否则返工成本最高。
- 把 QA 用例写进 `tests/` 后又说"测试已覆盖"，职责混淆。
- 交接文档只写"已完成"，QA 无法判断测什么。
