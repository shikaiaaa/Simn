## 1. 背景

- **谁提的、场景是什么**：想在线上或到店买衣服的用户（需求方为纯工具类小程序主体）。用户原话（摘录）：
  「根据用户外貌体型生成一个用户虚拟人物形象……根据上传衣服照片，来模拟自己穿上衣服的样子，看是否合身……
  支持放大查看穿着细节」。原始需求见 RQ-0001 第二节 R1–R4。
- **现在怎么解决、哪里不爽**：线上买衣服只能看模特图，无法判断穿在自己身上的视觉效果与大致尺码，退货率高；
  线下试穿受门店、时间、库存限制。用户缺一个「先看自己穿」的低成本工具。
- **为什么现在做**：2D 虚拟试穿已有可购买的商用服务（服务端异步生成），小程序端只承担采集、上传、轮询、展示，
  工程上可落地；3D 形象与精确合身依赖 WebGL 可用性、人体参数化与服装版型库，成本高一个量级，故按三期推进。
- **不做会怎样**：需求方无法验证 2D 试穿这条产品方向是否成立；用户继续盲买，退换货成本无法降低。
- **P1 的「虚拟形象」是什么**：P1 中「虚拟形象」= 用户上传照片经服务端 2D 换装后的**试穿效果图**，
  不是 3D 模型、不是独立生成的无服装形象图（后者见「明确不做」与 Q-2）。
- **P1 的交付形态**：**内部 demo**，供需求方内部验证 2D 试穿效果；不做提审、不选类目、不办资质、不面向真实用户发布。
  「上线版」另立需求（Q-17，详见 §3.3）。

## 2. 目标

做完之后，需求方可以在内部 demo 中完成一次完整闭环：
**上传 1 张全身正面照（可选补充最多 2 张）+ 身高/体重（性别、三围选填）+ 1 张单件上装照片 → 96 秒内得到 1 张可双指放大
查看细节的 2D 试穿效果图 + 一个参考尺码区间 → 随时一键删除自己的照片与生成结果。**

真实度口径（Q-1）：结果图须**保留可辨认的本人特征**（体型、肤色、发型、穿衣贴合效果），
**不承诺像素级像本人**，面部允许 AI 重绘。对外文案不得使用「真人级」「100% 还原」「像素级」等承诺性表述。

## 3. 范围

### 3.1 做

| 编号 | P1 范围项 | 说明 |
|---|---|---|
| S1 | 身体与人像采集 | 人像照片 1 张（全身正面）必填，可选补充最多 2 张（合计 ≤3）；身高、体重必填；**性别选填**（默认 `unspecified`，可跳过，跳过不阻塞生成）；胸围/腰围/臀围选填（Q-4、Q-5）；每项可单独重拍/修改 |
| S2 | 衣服采集 | 单件上装照片 1 张，仅接受用户**翻拍自家衣服**，平铺或挂拍（Q-3、Q-7） |

| S4 | 2D 试穿生成 | 服务端异步生成；每次产出 1 张静态结果图，长边 ≥2048px 优先（Q-11，降级规则见 BR-6） |

| S6 | 细节查看 | 结果图支持 1x–3x 双指缩放、放大后平移、复位；放大后纹理可辨、无可见接缝 |
| S7 | 进度与失败 | 阶段进度、96 秒上限、超时/失败原因、重试；禁止静默失败与占位图 |
| S8 | 删除 | 「删除本次数据」一键删除；「删除全部数据」入口；删除即物理全删、云端不留任务墓碑/时间戳（CP-08）；删除后服务端不再持有 |
| S9 | 合规 | 小程序内隐私单独同意、敏感信息最小化、AI 显式标识、18+ 声明；demo 不做提审/类目/资质 |
| S10 | 额度 | 普通用户 **1 次/日**、VIP 用户 **10 次/日**，每日 00:00 重置（Q-12）；端上显示剩余次数与 VIP 标识 |
| S11 | 上传照片自动适配 | 人像照与衣服照统一：长边 >4096px **或** 字节 >10MB 时**端上自动压缩**（保持 EXIF 方向、非 JPG 转 JPG），压缩后仍 >10MB 再降到长边 ≤3072；压缩后仍不合格才拒绝；长边 <1024px 仍拒绝并提示重拍（不放大）（m03503，详见 BR-12/AC-27）；v0.8 起压缩的**最终目标**对齐供应商规格（长边 ≤4096px 且 ≤5MB），L0 的 10MB/4096 仅作粗筛，详见 BR-14/AC-29 |
| S12 | 低版本客户端兜底 | 启动时检测 Skyline 可用性（`wx.getSkylineInfo` 缺失或返回不支持 = 低版本，约微信 <8.0.30 / 基础库 <3.0.0）；低版本一律走**原生弹窗**提示升级，不得进入业务、不得白屏、不得静默失败（详见 BR-13/AC-28） |

### 3.3 P1 交付形态：内部 demo

用户确认（Q-17 原话）：「先完成 demo，不进行上线处理，暂时不考虑上线需要的审核/资质问题」。

- **交付物**：一个可运行的小程序 demo，供需求方内部验证 2D 试穿效果与交互（采集 → 生成 → 放大查看 → 参考尺码 → 删除）。
- **不做**：不提审、不选服务类目、不办资质、不对外发布、不投放真实用户；不做上线版所需的合规文案法务定稿与压测。
- **不豁免的底线**（demo 阶段仍必须满足）：小程序内隐私单独同意与第三方受托处理方披露（BR-11）、人体照片最小化与删除（BR-8/9）、
  AI 生成内容显式标识（BR-10）、无导购/销售元素（BR-10）、禁用动态代码等平台硬约束（§6.5）。
- **上线版**：另立需求（如 REQ-000x），基于本 demo 的验收结论重新评估类目、资质、合规与容量。

demo 与上线版差异清单（上线版需求必须逐项补齐）：

| 事项 | P1（内部 demo） | 上线版（另立需求） |
|---|---|---|
| 服务类目与资质 | 不做选择、不办资质 | 必须选择类目并办理资质 |
| 提审与审核 | 不提审 | 必须提审并应对审核意见 |
| 微信内容安全接入 | 不接入；由生成服务方自带审核兜底（Q-16） | 必须接入微信内容安全，含误判申诉/重试路径 |
| AI 隐式标识（文件元数据） | 不强制；仅界面显式标识 | 必须写入生成合成属性、服务提供者编码、内容编号 |
| 删除与审计 | 删除即物理全删、不保留任务墓碑/时间戳（CP-08） | 如法务要求删除审计/对账，需新增最小审计字段（不含照片与围度，RK-11） |

| 对外 SLA 与客服 | 不承诺 SLA（Q-18） | 明确可用性目标与客服流程 |

## 4. 用户故事

| 编号 | 对应用户故事 |

| US-6（支撑·删除） | 作为用户，我希望一键删除我上传的照片和生成结果，且删除后服务端确实不再持有（物理全删、不保留任务记录），以便我随时撤回授权。 |
| US-7（支撑·额度） | 作为用户，我希望看到今天剩余生成次数、我是否为 VIP 以及重置时间，额度用完时明确提示，以便我不会白等或反复重试。 |

## 5. 业务规则

| 编号 | 规则 | 说明与可验证点 |
|---|---|---|
| BR-1 | 输入项与必填 | 人像照片 1 张（全身正面）必填，可选补充最多 2 张（合计 ≤3，Q-4）；身高（100–250cm，整数）、体重（25–250kg，1 位小数）必填；**性别选填**：`gender` ∈ {`male`, `female`, `unspecified`}，默认 `unspecified`，可跳过，跳过不阻塞生成（CP-06）；胸围/腰围/臀围（40–200cm，1 位小数）**选填**，缺失时不给尺码区间但不阻断生成（Q-5）；衣服照片 1 张。缺项或越界一律禁止提交，并提示具体缺哪一项。 |
| BR-2 | 人像照片合格性判定 | 必须同时满足：单人、全身可见（含脚部）、面部无遮挡、身体直立正面、非坐/蹲/躺、光线正常非逆光、非多人。任一项不满足即判定不合格；不合格必须阻断生成并给出**具体原因 + 重拍建议**，禁止仅提示「照片有问题」。服务端二次校验以生成服务返回结果为准，端上预检只做拦截不做放行承诺。 |
| BR-3 | 衣服照片合格性判定 | 仅接受用户**翻拍自家衣服**、**平铺或挂拍**、单件上装、完整展示、无遮挡、背景尽量纯色、可识别服装区域（Q-7）；模特上身图、电商商品图、吊牌特写、多件衣物、套装、鞋/配饰均不合格。不合格必须阻断并提示重拍，禁止提交生成。 |

## 6. 约束

### 6.1 技术基线与端上边界

- 技术基线：**skyline 渲染器 + glass-easel + 自定义导航栏**（`miniprogram/app.json` 现状），页面四件套与 `app.json` 注册必须同步（AGENTS.md 小程序专项门禁 §1）。该基线经用户 2026-11-11 拍板**保持不变**（低版本兼容方案 A：保留 skyline + 升级提示兜底，不改为 webview；见 BR-13）。
- **小程序端不做任何推理**（决策 C1）：人体重建、换装生成、尺码区间计算全部在服务端完成；端上只做采集、上传、轮询、展示。禁止引入端侧模型/WASM 推理方案。
- 双指缩放必须在 skyline 下可用；具体实现方式属 SE 技术方案，不在本 REQ 决定。该能力属**风险项**，见 §6.6。
- **上传前压缩边界**（BR-12）：自动适配仅允许使用小程序原生能力（如 `wx.getImageInfo` / `wx.compressImage` / Canvas 2D），**不得引入第三方图像处理库**；压缩属采集预处理，不是端侧推理，不违反「端上不做推理」。
- 压缩耗时计入「上传前处理」：不占用生成轮询的 96 秒，但计入用户可感知的端到端时长；若真机实测单张压缩明显拖慢整体体验或导致 AC-7 不可达，须登记为风险并由 SE 在 SPEC 中给出降级方案，不得静默延长等待。

### 6.2 网络与异步

- `wx.request` 存在**60 秒级硬超时**（平台默认 60s），任何单次请求都不得依赖超过 60 秒的同步等待；生成必须走**服务端异步任务 + 小程序轮询**（决策 C1）。
- 请求域名必须已在公众平台配置；HTTPS；本地调试的「不校验合法域名」不得进入提交版本（即使 demo 也按此登记在 DEV 交接文档）。
- 上传大图、轮询、结果下载分别有失败路径与超时上限，不得因单个请求超时导致页面卡死；照片压缩在 `wx.uploadFile` 之前完成，不占用请求 60 秒超时窗口。

### 6.3 包体积硬预算

- 主包 ≤2MB、单个分包 ≤2MB、全部分包合计 ≤20MB；**超限即 FAIL**（AGENTS.md 小程序专项门禁 §2）。
- 新增第三方库、图片、字体、3D 资源前，必须在 SPEC 的包体积预算表登记预计增量；未登记的实现不予验收。
- `docs/`、`tests/`、`tools/` 不得位于 `miniprogramRoot` 内；优先分包 + `lazyCodeLoading: requiredComponents`。

### 6.4 隐私与合规

- 人体照片属于敏感个人信息：**单独同意、最小化收集、可删除**三件套缺一不可；同意在小程序内首次使用点击完成（BR-11）。
- 性别为新增收集项但为**选填**，同意页须披露；不填不影响生成与参考尺码（CP-06、BR-11）。
- 删除即物理全删、云端不保留任务墓碑/时间戳（CP-08、BR-8）；仅同意审计记录保留（openidHash / 同意版本 / 时间 / 撤回记录），不含照片与围度。
- 相册/摄像头等隐私类 `wx.*` API 必须在《用户隐私保护指引》登记用途、触发时机、拒绝后的降级路径；未登记不得调用（AGENTS.md 小程序专项门禁 §3）。
- **供应商与接收方口径**：P1 试穿 API 已定为**火山引擎「图片换装 V2」**（境内，cn-north-1）；人体照片在境内处理，**不构成数据出境**。同意页与隐私文本仍须披露第三方受托处理方（北京火山引擎科技有限公司，境内）名称/所在地、处理目的、数据类别；demo 以「同意页披露 + 单独同意」为基线。**兜底**：若未来改用境外供应商，须恢复境外接收方披露 + 出境合规评估，并再次变更 BR-11（Q-9 历史答复保留，见 §10）。
- 成本：单次试穿 API 成本上限 **≤2 元/次**（Q-21，用户 2026-11-10）；超出需先报用户批准预算；demo 优先使用供应商免费/试用额度；上线前按真实报价复核。
- 内容安全：demo 阶段**不接入**微信内容安全接口，由生成服务方自带审核兜底（Q-16）；上线前必须接入（§3.3）。
- 类目：P1 demo **不选服务类目、不办资质、不提审**（Q-17）；上线版按纯工具类（无电商导购/销售/商家合作，决策 C2/C3）另立需求确认。
- AI 生成内容标识：demo 只强制界面显式标识；隐式标识（文件元数据）列入上线前（§3.3），用户协议须说明标识方法与样式。
- 未成年人：18+ 声明 + 条款禁止，不做实名核验（Q-15）。
- 端上压缩不改变隐私口径：原图与压缩中间产物不得写入 Storage（同 BR-9），上传服务端的仍是压缩后的单张图；BR-8/BR-9 的物理全删与 24h 留存不变；「已自动压缩」提示不得附带收集额外信息。

### 6.5 代码禁用项

- 禁止 `eval`、`new Function`、动态拼接 `require` / `import()`（小程序运行时不支持，且会被审核判为动态代码）。
- 不修改仓库外路径；小程序相关自动化脚本一律放 `tools/`。

## 7. 验收口径

判定原则：每条 AC 都能被**单个测试用例**验证；涉及第三方 API 的用例在测试环境用 mock / 契约桩驱动；
视觉类用例使用固定样张 + 明确的通过/不通过标准，不使用主观感受类表述。
测试素材（全身/半身/遮挡/多人/逆光/吊牌/多件衣物/模特上身图/电商图/超大分辨率/超大字节/低分辨率）随 QA 用例固化，后续迭代复用同一套。

- [ ] **AC-1 采集必填与数值校验**（自动化）：人像照片 0 张、衣服照片缺省、身高/体重缺省任一情况，「开始生成」为禁用态；绕过 UI 直接调用提交接口返回 4xx 并提示缺失项名称；三围留空不拦截（Q-5）；**性别不选不拦截、按默认 `unspecified` 处理**（CP-06）；身高/体重/三围越界或非数字时拦截。
- [ ] **AC-2 非全身照片拦截**（自动化）：输入固定「半身照」素材，上传完成 ≤5 秒内出现「非全身/未拍到脚部」原因提示，且生成任务创建接口调用次数 = 0。
- [ ] **AC-3 遮挡照片拦截**（自动化）：固定「手挡脸/衣物遮挡躯干」素材 → 出现「面部或身体被遮挡」提示；任务创建 0 次。
- [ ] **AC-4 多人照片拦截**（自动化）：固定「双人合照」素材 → 出现「照片需为单人」提示；任务创建 0 次。
- [ ] **AC-5 逆光/过暗照片拦截**（自动化）：固定「逆光欠曝」素材 → 出现「逆光/光线不足」提示；任务创建 0 次。
- [ ] **AC-6 失败路径禁止出图**（自动化）：mock 服务端返回照片校验失败（如服装/人体区域未识别）→ 页面停留校验失败态，结果区域不得出现任何图片（含占位图、缓存图），不得进入「生成中」。
- [ ] **AC-7 端到端 96 秒出图**（自动化 + 测试环境真网络）：固定标准素材（全身照 1 张 + 上装 1 张 + 合法数值），计时边界 = `createTask` 成功返回 → `taskGet` 返回 `SUCCEEDED` 且结果图可访问（`onload` 完成）；端到端 ≤**96 秒**；连续执行 3 次，3 次均满足；生成中 60 秒内正常显示进度，60–96 秒继续等待并可提示「生成较慢，请稍候」，不得在 60 秒判超时；结果页同时出现参考尺码区间与免责文案。96s 来源：2026-11-11 真实火山引擎实测供应商 67.3s / 端到端 69.5s（证据 `docs/dev/DEV-0001.md` §DEV-0001-48）+ 余量，用户拍板放宽（见 §10.6）。
- [ ] **AC-8 生成进度可见**（自动化）：生成过程中页面展示当前阶段（上传中/排队/生成中/完成）与已等待秒数；mock 驱动任务状态迁移，断言 UI 状态随状态变化、等待秒数随时间递增。
- [ ] **AC-9 超时态**（自动化，可控时钟）：mock 服务端 96 秒内不返回成功 → 96–101 秒之间进入超时态，显示失败原因与「重试」按钮；不展示结果图；页面不得持续转圈；同时断言 60 秒时仍为生成中（不得提前判超时）。
- [ ] **AC-10 失败原因分类**（自动化）：分别 mock 三类错误：①额度已用完（普通第 2 次/VIP 第 11 次）②内容安全拦截（demo 由生成服务方返回）③服务不可用（先显示排队态与已等待时长，再给失败文案）→ 页面显示三组不同中文原因与下一步动作，不得统一显示「失败请重试」；全程无结果图。
- [ ] **AC-11 生成额度（普通 1 次 / VIP 10 次）**（自动化）：按测试配置分别以普通账号与 VIP 账号验证：普通第 1 次成功、第 2 次被拦截并提示「今日额度已用完，明日 00:00 重置」；VIP 第 10 次成功、第 11 次被拦截；端上均显示剩余次数，VIP 账号显示 VIP 标识；被拦截时任务创建接口调用 0 次；失败/超时后剩余次数恢复（Q-13）。
- [ ] **AC-12 任务恢复与幂等**（自动化）：生成中退出页面再进入 → 恢复同一任务（任务 ID 相同）的进度或结果；服务端任务创建调用 1 次、额度扣减 1 次。
- [ ] **AC-13 双指缩放交互**（自动化，模拟器/真机手势）：结果图支持 1x–3x 双指缩放、放大后平移、双击或按钮复位到 1x；缩放与平移边界不越界、图片不变形、不出现白屏。
- [ ] **AC-14 放大画质**（自动化尺寸断言 + 人工视觉用例）：默认分支结果图源文件长边 ≥2048px，3x 下与源图 1:1 裁切对比，3 组固定样张衣物纹理边缘均可分辨、无块状马赛克；若走降级分支（Q-11），须同时满足长边 ≥1536px、3x 纹理可辨、且存在用户复核记录；两种分支均要求 3/3 通过。

## 8. 后续路线图

> 决策 A1：本节只写**范围与前置条件**，不写规格、不写 AC；均不构成本 REQ 的交付承诺。

### P1.1 · 单件下装 / 裙装 / 外套（用户确认 Q-3）

- **范围**：在 P1 上装能力基础上扩展单件下装、裙装、外套的 2D 试穿；仍为单件、不含叠穿与上下装组合。
- **前置**：P1 demo 验收通过；所选用 API 对下装/裙装/外套的能力与输入要求已验证；品类扩展不得改变 P1 的隐私、删除与标识约束。

### P2 · 轻量 3D 形象（可旋转）与历史形象库再评估

- **范围**：在 P1 的采集数据基础上，生成轻量 glTF 形象，支持旋转查看与多角度观察；沿用 P1 的隐私同意与删除机制。历史形象库是否纳入 P2 由届时评估（Q-19）。
- **前置条件**：
  1. WebGL / xr-frame 在 skyline 渲染器 + glass-easel 下的可用性验证（含真机机型矩阵）；
  2. 人体参数化拟合（照片 + 数值 → 体型参数）可行性与误差评估；误差不得对外表述为「量体」；
  3. 分包体积预算：glTF 模型与纹理资源计入分包 ≤2MB、总计 ≤20MB 的分配方案；
  4. 3D 资产与历史形象的生命周期、删除链路、留存合法性评估。

### P3 · 精确合身判断

- **范围**：基于服装真实版型数据给出部位级合身结论（松紧、建议尺码、风险提示），替代 P1 的参考区间。
- **前置条件**：
  1. 服装版型库与尺寸表（品牌/供应商提供，含面料弹性等参数）；
  2. 商家合作与版型数据授权；届时需重新评估类目、资质与商家关系（决策 C2/C3 仅约束本项目纯工具定位）；
  3. 规则引擎与尺码标准（国标/品牌尺码表二选一或映射）；
  4. 客服与售后口径：合身结论的免责与责任边界。
